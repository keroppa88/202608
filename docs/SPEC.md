## 1. 目的

海外の主要株価指数・セクター指数・REIT指数・商品指数・為替・個別銘柄、および日本の
主要指数・銘柄について、**日次の四本値（始値・高値・安値・終値）を継続的に記録する**。

### 背景にある要件

当初はスプレッドシート上で `GOOGLEFINANCE` 関数を並べる方式を検討したが、以下の理由で採らない。

- 銘柄数が増えるほど再計算が重くなり、全体が一括で失敗する
- 取得に失敗しても**エラーにならず空欄になる**ため、更新不全に気づけない
- 成否の記録・再試行・通知ができない

したがって本仕様は **「1銘柄 = 1リクエスト、成否を個別に記録する」** ことを中核に置く。

---

## 2. 設計方針

### 2.1 生データを無加工で保存し、抽出は後段で行う

取得したレスポンスは**一切加工せずそのままファイルに保存**する。四本値の抽出は
保存済みファイルを入力とする別処理として実装する。

理由:

- 抽出ロジックを変更しても、**再取得なしで過去分をやり直せる**
- 配信側のフォーマットが変わっても生データが残るため、原因を追跡できる
- 「取得失敗」と「抽出失敗」を別々の事象として扱える

### 2.2 ウェブページは「見たままのテキスト」で扱う

人が画面を全選択してコピーしたものと同じテキストを丸ごと保存し、
**そのテキストだけを入力に抽出する**。タグ・クラス名・属性・XPath は一切参照しない。

判断の手がかりは、人が画面を見て使うのと同じものにする。

- 掲載日時は「2026年8月10日 15:48」という形で1行に現れる
- 題名はその近くにある、いちばん長い行
- 本文はその下に続く長い行の連なり

取得手段は2つあるが、得られるテキストは同じなので抽出側は区別しない（`src/page_text.py`）。

| 手段 | 用途 |
|---|---|
| `capture(url)` | ヘッドレスブラウザで開いて表示テキストを取る。JavaScript描画やボット判定のあるページ |
| `text_from_html(html)` | 取得済みHTMLを表示テキストに変換する。中身が静的HTMLに入っているページ |

例外は**リンク先URL**のみ。画面に表示されない情報なので HTML から拾う。
これは人がリンクをクリックする動作に相当し、記事の中身の解釈ではない。

### 2.3 銘柄ごとに独立して取得する

1銘柄の失敗が他の銘柄に波及しない構造とする。取得は銘柄単位でリトライし、
失敗した銘柄のみをエラーとして記録する。

### 2.4 「成功したように見える失敗」を必ず検知する

HTTP 200 が返っても中身が正しいとは限らない。以下を必須チェックとする。

| チェック | 内容 |
|---|---|
| 値の型 | 価格が数値であること（null・空文字を弾く） |
| 鮮度 | 取引所側タイムスタンプが一定日数以内であること |
| 四本値の整合性 | 安値 ≤ 始値/終値 ≤ 高値 が崩れていないこと |
| 銘柄同一性 | 配信元が返す銘柄名が期待と一致すること |

**四本値の整合性について。** 高値が終値より安い、といった足は物理的にありえず、
値幅やローソク足の計算を壊す。実測では 2,042行中11行（0.5%）で崩れていた。
Yahoo の為替データが常時持っている性質で、大半は 0.005〜0.05% の集計差。

- **許容幅 0.1%**（`OHLC_TOLERANCE`）。丸め誤差の範囲は通す
- **最新の足**が超えたらエラー。その日届いたばかりの異常なので気づけるようにする
- **過去の足**が超えたらその足だけ除外し、記録に残す。エラーにはしない
  （1か月分を毎回取り込むため、エラーにすると同じ異常を3週間通知し続けることになる）
- **値は書き換えない。** 配信元にない数字を作らない（§2.1）

**§9 の検証記録に、実際にこの罠へ落ちた事例を残してある。**

## 3. データソース

### 3.1 採用（検証済み）

#### Yahoo Finance chart API

```
https://query1.finance.yahoo.com/v8/finance/chart/{symbol}?interval=1d&range=5d
```

- 認証不要。1リクエスト = 1銘柄
- レスポンスは JSON。`indicators.quote[0]` に四本値、`meta` に通貨・取引所・タイムスタンプ
- `meta.exchangeName` に配信元取引所コードが入る（`SNP` = S&P Dow Jones、`GER` = XETRA 等）
- **非公式API**。予告なく仕様変更・停止の可能性がある

#### MOEX ISS API（ロシアRTS）

```
現在値: https://iss.moex.com/iss/engines/stock/markets/index/securities/RTSI.json
履歴:   https://iss.moex.com/iss/history/engines/stock/markets/index/securities/RTSI.json?from=YYYY-MM-DD
```

- モスクワ取引所の公式データサービス。認証不要。ドキュメントは `https://iss.moex.com/iss/reference/`
- **履歴を期間指定で一括取得できる**ため、取得漏れを後から遡って復旧できる
- 注意: `iss.moex.com/robots.txt` は `Disallow: /`（§10 参照）

#### 日経「東証大引け」記事

```
検索:   https://www.nikkei.com/search?keyword=東証大引け、&volume=2
記事:   https://www.nikkei.com/article/{記事ID}/
```

- **静的HTMLに全て含まれる。ヘッドレスブラウザは不要**（curl 相当の取得で足りる）
- 検索ページ（約1MB）に記事IDとタイトルが出現順に含まれる
- 記事ページの JSON-LD（`application/ld+json`）に `headline` と `datePublished` が入る
- 本文は `<p class="paragraph_...">` として記事セクション（`data-track-article-content`）内に格納
- 掲載時刻は大引け（15:00）の約50分後。実測値は 15:48:21

詳細は §4A。

## 4A. 日経「東証大引け」記事の収集

### 目的

平日の大引け後に掲載される「東証大引け」記事を、**本文ごと蓄積する**。
株価の数値そのものは §4 の各ソースから別途取得しているため、
ここで欲しいのは**記事の文章**である。

### 保存先

```
article/
├── japan202608.txt
├── japan202609.txt
└── japan202610.txt   …以降、年月ごとに1ファイル
```

- ファイル名は `japan{YYYY}{MM}.txt`
- 振り分けは**記事の掲載日（記事年月日）基準**。月末深夜に取得がずれ込んでも、
  8月31日の記事は `japan202608.txt` に入る
- 追記は時系列順（新しいものを末尾に追加）
- 文字コードは UTF-8、改行は LF

### レコード形式

```
================================================================================
題名      : 東証大引け　日経平均は3日ぶり反発　TOPIX最高値接近　米利上げ観測後退が追い風
記事年月日: 2026-08-10 15:48:21 JST
取得年月日: 2026-08-10 17:05:12 JST
URL       : https://www.nikkei.com/article/DGXZQOFL102V60Q6A810C2000000/
--------------------------------------------------------------------------------
10日の東京株式市場で日経平均株価は3営業日ぶりに反発し、終値は前週末比1363円51銭
（2.08%）高の6万6970円22銭だった。…

（以下、段落を空行区切りで全文）
```

保持する項目は4つ。

| 項目 | 取得元 |
|---|---|
| 題名 | JSON-LD `headline` |
| 記事年月日 | JSON-LD `datePublished` |
| 記事本文 | 記事セクション内の段落を順に連結 |
| 取得年月日 | 実行時のシステム時刻 |

URL は再取得・重複判定のために併記する。

### 処理フロー

```
1. 検索ページを丸ごと保存                     ← 生HTML
2. 保存済みHTMLから記事IDとタイトルを全件抽出
3. 「東証大引け」で始まるもののうち、掲載日時が最新の1件を選ぶ
4. その記事ページを丸ごと保存                 ← 生HTML
5. 保存済みHTMLから 題名・記事年月日・本文 を抽出
6. 取得年月日を付けて article/japan{YYYYMM}.txt に追記
```

取得（1・4）と抽出（2・5）を分離し、抽出ロジックを変更しても再取得を不要とする（§2.1）。

**「一番上を取る」ではなく掲載日時で判定する。** 並び順に依存すると、
日経側が順序を変えた際に別の日の記事を静かに拾い続けることになり、
§2.4 で排除している「エラーにならない失敗」に該当する。

### 重複防止

**記事IDで判定する。** すでに同じIDが当月ファイルに存在する場合は追記しない。

これにより以下が自動的に処理される。

- 日本の祝日 — 記事が出ないため検索結果は前営業日のものになる。ID重複で追記されない
- ワークフローの再実行 — 二重追記されない
- cron の遅延・複数回起動 — 同上

「祝日カレンダーを持って判定する」方式は採らない。休場日の変更に追随できないため。

### 実行時刻

```
cron: "0 9 * * 1-5"     # UTC 月〜金 09:00 = JST 月〜金 18:00
```

掲載実測が 15:48 のため、JST 18:00 に余裕を持って起動する。
JST 18:00 は UTC では同日 09:00 なので、曜日はずれない（§8 の一覧参照）。
GitHub Actions の cron は数十分遅れることがあるが、記事は掲載済みのため影響しない。

祝日にも起動するが、上記の重複判定により**何も追記せず正常終了**する。
これは失敗ではないため、ワークフローを fail させない。

## 4B. 日経「米国株」大引け記事の収集

### 検索

```
https://www.nikkei.com/search?keyword=米国株、　NQNニューヨーク　米株式市場でダウ工業株30種平均は&volume=10
```

§4A と同じく静的HTMLで題名・掲載日時・本文が取得できる（実測 9段落・1,194文字）。

保存先は `article/us{YYYYMM}.txt`。形式・月ファイルの振り分け規則は §4A と同一。

### この検索は1営業日につき3本ヒットする

キーワードが**本文**に一致するため、東証大引け（題名一致）と違い3種類とも拾ってしまう。

| 掲載時刻(JST) | 題名の特徴 | 本文の「終値」 | 種別 |
|---|---|---|---|
| 22:30頃 | 「…で始まる」 | なし | 寄り付き |
| 05:07頃 | 値幅の記載なし | あり | 引け速報 |
| **05:36頃** | **「◯◯ドル高 / ◯◯ドル安」** | あり | **大引け ← 対象** |

実測10件すべてでこの規則が成立した（151ドル高 / 464ドル安 / 263ドル高 / 907ドル高）。

### 選択ロジック

```
1. 掲載日時の新しい順に候補を見る
2. 題名が「数字＋ドル高／ドル安」を含む
3. かつ本文に「終値」を含む
4. 最初に一致したものを採用
5. 10件見て該当しなければエラー（黙って別の記事を入れない）
```

**位置だけに頼らない。** JST 22:30 を過ぎると検索結果の先頭が寄り付き記事に変わるため、
「一番上」で取ると実行時刻の変更や遅延で静かに別種の記事を拾い続けることになる。

### 実行スケジュール（確定）

大引け記事はまず速報的に掲載され、**5時台から7時の間に最終版になる**。
必要なのは各日の最終版のみ。**JST 07:00** に起動する（§8 の注意点も参照）。

```
cron: "0 22 * * 1-5"     # UTC 月〜金 22:00 = JST 火〜土 07:00
```

米国市場は月〜金に取引され、その大引け記事は翌朝 JST に掲載される。
したがって日本時間では**火曜の朝から土曜の朝**が稼働日となる。

**cron は UTC で解釈されるため、曜日の指定に注意が必要。**
JST 08:00 は UTC では前日 23:00 にあたるので、
「JST 火〜土」を表すには UTC 側で `1-5`（月〜金）と書く。

| UTC | JST |
|---|---|
| 月 22:00 | 火 07:00 |
| 火 22:00 | 水 07:00 |
| 水 22:00 | 木 07:00 |
| 木 22:00 | 金 07:00 |
| 金 22:00 | **土 07:00** |

> 注意: 重複判定は記事IDで行うため、**一度取得するとその版で確定する**
> （後から最終版が出ても記事IDが同じならスキップされる）。1日1回の起動を前提とする。
> cron の遅延は最終版の確定を待つ方向に働くため、遅れる分には問題ない。

米国市場の休場日（感謝祭など）には記事が出ないため、検索結果は前営業日のものになる。
記事IDの重複判定により**何も追記せず正常終了**する（§4A と同じ扱い）。

### 取引日と掲載日のずれ

米国 8月7日（金）の取引は **8月8日（土）05:36 JST** に掲載される。
月ファイルの振り分けは掲載日基準のため、米国 8月31日の取引は `us202609.txt` に入る。

## 4D. JPX の株価指数

```
https://www.jpx.co.jp/markets/indices/realvalues/01.html
```

TOPIX・JPXプライム150・JPX日経インデックス400・東証REIT指数、
33業種別・TOPIX-17・規模別・スタイル別・市場別など、
このページに載っている指数をまとめて取る。

### 取得方法

数値は JavaScript で描画され、**静的HTMLには入っていない**（55KBのHTMLに `4,074.93` が0件）。
ブラウザで開いて表示テキストを取る（§2.2）。

`www.jpx.co.jp/robots.txt` は `Disallow:` が空で、**全パスが許可されている**。
日経の指数サイトと違いボット判定もない。

### 表の読み方

タブ区切りで次の並びになっている。

```
指数名 → 現在値 → 前日比 → 前日比% → 始値 → 高値 → 安値 → （グラフ列）
```

始値・高値・安値が `--` の指数は現在値だけが公表されている（配当込みTOPIX、
TOPIX Micro Cap、スタイル別の一部など）。空欄として記録する。

### 出力

`data/jpx_index.csv`

| 列 | 内容 |
|---|---|
| `trade_date` | ページに日付表記があればそれ。無ければ実行日（JST） |
| `name` | 指数名 |
| `open` / `high` / `low` / `close` | 四本値。`close` は「現在値」= 大引け後なら終値 |
| `change` / `change_pct` | 前日比・前日比% |
| `fetched_at` | 取得時刻 |

### 休場日に架空の足を作らない

**休場日もページは前営業日の値を出し続ける。** 実行日を取引日として記録すると、
存在しない日の足を全指数ぶん作ってしまう。

対策は**値そのものでの判定**。前回記録した日と**全指数の終値が一致**したら、
休場日とみなして記録しない。祝日カレンダーは持たない（休場日の変更に追随できないため。
§4A の記事の重複判定と同じ考え方）。

1指数でも動いていれば通常どおり記録する。全指数が完全一致するのは休場日だけである。

### 蓄積しない指数

生テキストには**ページの全内容を残す**が、CSV には入れないものがある。
レバレッジ・インバース系と為替ヘッジ系で、いずれも原指数から機械的に導けるため。

判定は指数名に次の語が含まれるかで行う（`EXCLUDE_KEYWORDS`）。

```
レバレッジ / インバース / ダブルインバース / ベア / ブル
為替ヘッジ / ドルヘッジ / ユーロヘッジ
```

除外した指数名は実行ログに出す。過不足があれば語を足し引きして調整する。

### 取りこぼしの検知

描画不足は**取得できた指数の数**で見る。前回記録した日の指数数の8割
（初回は50）を下回ったらエラーにする。除外行の割合では見ない。

検査は**書き込むより前**に行う。中途半端な結果を残さないため
（ワークフローの commit は `if: always()` なので、書いてしまうと失敗した実行でもコミットされる）。

四本値の整合性（安値 ≤ 始値/終値 ≤ 高値）も相場データと同じ 0.1% で検査し、
崩れた指数はその指数だけ落として記録に残す（§2.4）。

同じ指数が複数の節に載っている（TOPIX、東証REIT指数など）。最初の1件を採る。

### 実行

`.github/workflows/jpx-index.yml`。JST 月〜金 18:00。


「ご注意」の文中にも現れるため、前方一致だと表の外を拾ってしまう。

見出し行は**先頭のセルが空**であることで見分ける。それ以外のタブ行は
先頭が項目名、残りが列の値。

| 列 | 内容 |
|---|---|
| `trade_date` | ページの「8/7(金)」から。年はページに無いので実行日から補う |
| `group` | 取引動向 / 信用取引指標 / 先物指標 |
| `section` | 表題 |
| `item` | 行の見出し |
| `column` | 列の見出し |
| `value` / `unit` / `note` | 値・単位・括弧書きの注記 |

項目数が多く列が揃わないため長形式にする。

`※倍率` や `新規牛熊比率(%)` のように**列に属さない単独の値**も、
見た目の位置どおり最初の列に割り当てる。ページの見え方をそのまま写す方針
（§2.2）に従い、意味づけによる並べ替えはしない。

同じ `(trade_date, group, section, item, column)` は上書きするので、
休場日に実行してもページの日付が変わらず、架空の値は増えない。

取れた項目が25を下回ったらページの作りが変わったと疑い、**書き込む前に**エラーで止める。

`.github/workflows/matsui.yml`。JST 火〜土 07:00（朝の部）。
前営業日更新分なので、土曜の朝に金曜分が取れる。

## 6. 出力形式

相場データは **`data/overseas.csv` の1ファイル**にまとめる。**1行 = 1銘柄の1日**（長形式）。

| 列 | 内容 |
|---|---|
| `trade_date` | 取引日。**取引所ローカルの日付**（UTC に直すと市場ごとに1日ずれる） |
| `category` | 分類（海外指数 / セクター / REIT / 商品 / ETF / 為替 / 個別株） |
| `name` | 表示名 |
| `symbol` | シンボル |
| `source` | データソース（`yahoo` / `moex`） |
| `open` / `high` / `low` / `close` | 四本値 |
| `volume` | 出来高。取れない銘柄は**空欄**（0 とは区別する） |
| `currency` | 通貨 |
| `exchange` | 配信元取引所コード |
| `fetched_at` | 取得実行時刻（JST, ISO8601） |

### 銘柄ごとにファイルを分けない理由

銘柄を追加・削除してもファイル構成が変わらず、読み込みが1回で済み、
同じ日の市場横断比較がそのままできる。年間約19,000行（2〜3MB）で、
10年貯めても表計算ソフトの行上限に届かない。
後から銘柄ごとに分割するのは容易だが、逆は手間がかかる。

日付を行・銘柄を列にする横形式は採らない。銘柄を1つ足すだけで列構成が変わり、
過去の行と噛み合わなくなるため。

### 毎回、取得できた確定足をすべて取り込む

Yahoo は1か月分、MOEX は14日分の足を返すので、最新1本だけでなく**全部**を
`(trade_date, symbol)` をキーに追記する。これにより:

- 取得を1日飛ばしても、次の実行で自動的に埋まる
- 休場日はそもそも足が存在しないため、**「更新なし」と「取り逃し」を区別する必要がない**
- 国ごとに休場日が違っても、追加の判定を持たずに済む

### 注意

- **取引日は銘柄ごとに異なる。** 実行時刻によって、欧州・アジアは当日、
  米国は前営業日になる。日付列を必ず参照すること
- 出来高 0 を異常値として弾かないこと（指数では正常）
- **進行中のセッションは記録しない。** 取引時間中に叩くと Yahoo は未確定の足も
  四本値が埋まった状態で返すが、その `close` は終値ではない（§9 参照）

## 7. 失敗検知

| 事象 | 検知方法 | 動作 |
|---|---|---|
| HTTP エラー | ステータスコード | 指数バックオフで最大3回リトライ |
| 価格が null / 非数値 | 型チェック | 当該銘柄をエラーとして記録 |
| 時系列が空 | `timestamp` の有無 | 配信停止の疑いとして記録 |
| 値が古い | 取引所タイムスタンプと現在日時の差 | 閾値超過でエラー |
| 銘柄の取り違え | `longName` と期待名の突合 | 初回登録時および定期的に目視確認 |

エラーが1件でもあればワークフローを **fail** させ、GitHub の通知経路で気づけるようにする。

**日次コミットの有無そのものが実行の証跡になる。**
コミットが無い日＝処理が走らなかった日、と判断できる。

### スケジュール一覧

**cron は UTC で解釈される。** JST の朝に動かすものは UTC では前日の夜になるため、
曜日の指定が1日ずれる。下表の対応で設定済み。

**朝の部（JST 07:00）** — 海外市場が閉じた後にまとめて取る

| ワークフロー | cron（UTC） | 起動（JST） | 内容 |
|---|---|---|---|
| `market.yml` | `0 22 * * 1-5` | **火〜土 07:00** | 海外指数・為替・セクター・REIT・商品・個別株（90件） |
| `matsui.yml` | `0 22 * * 1-5` | **火〜土 07:00** | 松井証券の投資指標（§4G。前営業日更新分） |
| `nikkei-us.yml` | `0 23 * * 1-5` | **火〜土 08:00** | 日経「米国株」大引け記事 |

**夕の部（JST 18:00）** — 東京市場が閉じた後にまとめて取る

| ワークフロー | cron（UTC） | 起動（JST） | 内容 |
|---|---|---|---|
| `japan-stocks.yml` | `0 9 * * 1-5` | **月〜金 18:00** | 日本株（23件）。朝の枠では東証が開く前で前営業日の足しか取れない |
| `nikkei-jp.yml` | `0 9 * * 1-5` | **月〜金 18:00** | 日経「東証大引け」記事 |
| `nikkei-index.yml` | `0 9 * * 1-5` | **月〜金 18:00** | 日経の指数ページ（§4C） |
| `jpx-index.yml` | `0 9 * * 1-5` | **月〜金 18:00** | JPX の株価指数（§4D） |
| `nikkei-kabu.yml` | `0 9 * * 1-5` | **月〜金 18:00** | 日経の国内株式指標（§4E） |
| `nikkei-rank.yml` | `0 9 * * 1-5` | **月〜金 18:00** | 日経の日本株ランキング（§4F） |

朝の部を JST 火〜土に置く理由は、その時点で
米国・欧州・アジアのいずれも**前営業日の引けが確定している**ため。
月曜朝は新しい確定足がないので対象外とする。

> **米国株記事のみ注意点がある。** 最終版が固まるのは5時台〜7時であり（§4B）、
> 07:00 起動はその境界にあたる。GitHub Actions の cron は数分〜数十分遅れる傾向があり
> 実際には 07:05〜07:30 頃の起動になるため実用上は問題ないが、
> **確実性を優先するなら 07:30 起動が安全**。
> 重複判定は記事IDで行うため、一度取得すると後から最終版が出ても上書きされない。

### concurrency グループは使わない

どのワークフローも同じブランチへ push するが、`concurrency` による直列化は行わない。

同一グループで待機中の run が2件以上になると、**古い方が自動でキャンセルされる**。
取得が1回まるごと消えるうえ、失敗としても記録されない。
§2.4 で排除している「エラーにならない失敗」そのものになる。

代わりに `.github/scripts/commit.sh` が push 競合時に rebase して最大5回再試行する。
夕の部は6本が同時刻に起動するため、`commit.sh` の再試行がここで効く。

### 制約

| 項目 | 内容 |
|---|---|
| cron の精度 | 数分〜数十分の遅延がある。混雑時はスキップされ得る |
| 60日ルール | リポジトリが60日間無活動だとスケジュールが自動停止する。日次コミットにより回避される |
| 実行時間 | 相場データ77銘柄で2〜3分。記事は各1分未満 |

## 10. ライセンス・公開に関する留意事項

本リポジトリは**公開**である。ページとして公開・宣伝する意図はなく、
取得データの倉庫として運用する方針で確定済み。以下は認識した上で運用する。

- Yahoo Finance は非公式APIであり、利用が明示的に許諾されているわけではない
- `iss.moex.com/robots.txt` は `Disallow: /`。ただし MOEX 自身が
  ISS を公開ドキュメント付きのデータサービスとして提供している
- 株価指数の指数値は本来ライセンス商品であり、再配布には制約があり得る
- 日経の記事本文は著作物である。`nikkei.com/robots.txt` は汎用の `User-agent: *`
  に対して `/article/` `/search` を禁じていないが、AI・スクレイピング系の
  エージェント（`ClaudeBot`、`GPTBot`、`Scrapy` など40件超）を名指しで全面拒否しており、
  データ利用は問い合わせ窓口（`nkbb.nikkei.co.jp`）へ案内している

### JPX API（有料）について — 要確認

**契約済みの有料データを公開リポジトリにコミットする場合、再配布にあたる可能性がある。**
利用規約を確認し、必要であれば以下のいずれかを採る。

1. 当該データのみリポジトリにコミットせず、Actions の Artifacts に保存する
2. リポジトリを非公開に変更する
3. 契約上問題ないことを確認した上でコミットする

認証情報は必ず **GitHub Secrets** に格納し、コードやログに出力しない。
